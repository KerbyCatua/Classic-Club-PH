# 1. Existing Infrastructure Assessment

## Current architecture

The project is currently a static, multi-page storefront with no PHP backend or database.

- HTML pages are located at the repository root.
- Shared header and footer markup are loaded dynamically from `components/`.
- Global styling is centralized in `assets/css/style.css`.
- Client-side behavior is implemented in `assets/js/`.
- Bootstrap, Bootstrap Icons, and Google Fonts are loaded from CDNs.
- Product, cart, wishlist, promotion, and illustrative order data are stored in browser `localStorage`.

### Existing page groups

| Area | Existing files |
|---|---|
| Marketing/content | `index.html`, `about.html`, `lookbook.html`, `contact.html`, `faq-shipping.html`, `size-guide.html` |
| Catalog | `shop-all.html`, `tops-tees.html`, `outerwear-hoodies.html`, `bottoms-accessories.html`, `new-arrivals.html`, `product-detail.html` |
| Shopping | `cart.html`, `checkout.html`, `order-confirmation.html` |
| Account | `auth.html`, `account-dashboard.html`, `wishlist.html` |

## Existing JavaScript responsibilities

### `store.js`

Contains:

- 16-product catalog.
- Product IDs, SKUs, names, categories, colors, prices, descriptions, image URLs, and new/core status.
- Cart storage and quantity changes.
- Wishlist storage.
- Promotion codes:
  - `CLASSIC10`
  - `FREESHIP`
- Fixed PHP 180 shipping fee.
- Illustrative order creation.
- Last-order persistence.
- Default seeded cart and illustrative fallback order.

Important observations:

- Product identity currently combines style and color, for example `essential-hw-tee-obsidian`.
- Size is stored as a cart attribute rather than catalog data.
- Inventory is not persisted; products are always presented as available.
- Orders use a fixed order number and illustrative fallback data.
- Unknown product IDs fall back to the Essential Heavyweight Tee, which should eventually become an explicit not-found response.

### `main.js`

Handles:

- Cart badge synchronization.
- Wishlist badge synchronization.
- Product detail hydration from `?id=`.
- Product image hydration.
- Wishlist button behavior.
- Favicon injection.

### `partials.js`

Loads:

- `components/header.html`
- `components/footer.html`

using `fetch()` and injects them into placeholder elements.

### `global-loader.js`

Provides the global loading overlay and reduced-motion behavior.

## Existing workflows

### Catalog workflow

1. User navigates through catalog pages.
2. Product cards contain product IDs.
3. `main.js` adds product query parameters.
4. `product-detail.html` is hydrated from `CCStore`.

### Cart workflow

1. User selects color, size, and quantity.
2. `CCStore.addToCart()` stores the item in `localStorage`.
3. `cart.html` reads and renders cart data.
4. User can update quantities, remove items, or move items to wishlist.
5. Checkout reads the same browser state.

### Checkout workflow

1. User enters contact and shipping details in `checkout.html`.
2. Payment methods are illustrative only.
3. `CCStore.placeOrder()` stores an illustrative order in `localStorage`.
4. The user is redirected to `order-confirmation.html`.

### Authentication workflow

The forms in `auth.html` currently prevent submission and redirect directly to the dashboard. There is no:

- Real account creation.
- Password verification.
- Session.
- Logout.
- Password reset.
- Authorization check.

### Account workflow

`account-dashboard.html` renders illustrative profile, address, wishlist count, and order information from `CCStore`.

### Contact workflow

`contact.html` contains an inquiry form with:

- Name.
- Email.
- Topic.
- Optional order number.
- Message.
- Optional JPG, PNG, or PDF upload.
- Consent checkbox.

It currently does not submit data to a backend.

## Strengths

- Clear visual separation between content, catalog, shopping, and account pages.
- Centralized reusable header and footer.
- Centralized client-side store module.
- Product identifiers are already consistently used across pages.
- Existing frontend can remain largely intact.
- Existing UX already identifies the future persistence requirements.

## Weaknesses relevant to database integration

- No backend validation.
- No server-side authentication or authorization.
- No persistent product, inventory, customer, order, wishlist, or inquiry records.
- Client-controlled prices and order totals.
- Client-controlled payment labels.
- Fixed order number.
- Static illustrative customer information.
- No CSRF protection.
- No server-side session.
- `localStorage` is not suitable for account-specific or trusted transactional data.
- Absolute URLs such as `/components/header.html` may require adjustment when hosted in an XAMPP subdirectory.
- External image URLs are used instead of locally managed product media.

## Components that should remain unchanged initially

- Visual styling in `assets/css/style.css`.
- Loading behavior in `assets/js/global-loader.js`.
- Marketing pages and content.
- Existing product card presentation.
- Header/footer visual design.
- Bootstrap-based layout.

The first integration should replace data and submission behavior, not redesign the frontend.

# 3. RBAC Architecture

## Roles

Initial seed roles:

| Role | Intended access |
|---|---|
| `super_admin` | All system functionality, including roles and permissions |
| `admin` | Administrative catalog, orders, users, and inquiries |
| `manager` | Operational catalog, inventory, and order management |
| `staff` | Assigned operational modules |
| `customer` | Personal profile, orders, addresses, and wishlist |
| `guest` | Public catalog and guest checkout |

`guest` may be represented as an application state rather than a database user.

## `roles`

| Column | Type | Constraints |

| `updated_at` | `DATETIME` | Not null |

- `catalog.view`
- `catalog.manage`

- `orders.view_all`
- `orders.manage`

- `users.manage`

- `inquiries.manage`
- `newsletter.manage`

| Column | Type | Constraints |
|---|---|---|
| `id` | `BIGINT UNSIGNED` | Primary key |
| `name` | `VARCHAR(120)` | Not null, unique |
| `display_name` | `VARCHAR(150)` | Not null |
| `description` | `VARCHAR(255)` | Nullable |
| `created_at` | `DATETIME` | Not null |

## `user_roles`

Supports multiple roles per user.

```text
UNIQUE (user_id, role_id)
```

Foreign keys:

- `user_id` → `users.id`
- `role_id` → `roles.id`

Recommended deletion rule: `ON DELETE CASCADE`.

## `role_permissions`

Associates roles with permissions.

```text
UNIQUE (role_id, permission_id)
```

Recommended deletion rule: `ON DELETE CASCADE`.

## `user_permissions`

Use only for explicit exceptions.

| Column | Type | Constraints |
|---|---|---|
| `user_id` | `BIGINT UNSIGNED` | Primary/foreign key component |
| `permission_id` | `BIGINT UNSIGNED` | Primary/foreign key component |
| `effect` | `ENUM('allow','deny')` | Not null |
| `created_at` | `DATETIME` | Not null |

Authorization precedence:

1. Explicit deny.
2. Explicit allow.
3. Role permissions.
4. Default deny.

Frontend visibility must never be treated as authorization.

```text

    ↓

    ↓

    ↓
```

Responses should be JSON with consistent success and error formats.

The frontend should never receive:

- Database credentials.
- Password hashes.
- Internal authorization details.
- Unfiltered database errors.
- Sensitive audit information.

## Checkout flow

1. Load cart from server or guest session.
2. Recalculate prices from database values.
3. Validate variants, sizes, quantities, promotion, and address.
4. Begin database transaction.
5. Lock or verify inventory.
6. Create order.
7. Create immutable order items.
8. Create order address snapshot.
9. Record promotion redemption if applicable.
10. Update inventory.
11. Convert the cart.
12. Commit transaction.
13. Return order number.
14. Redirect to confirmation page.

The browser must not be trusted for totals, prices, stock, order status, or payment status.

## Authentication flow

1. Submit credentials over localhost HTTPS if configured, otherwise restrict usage to local development.
2. Validate email and password.
3. Query the user by email.
4. Verify with `password_verify()`.
5. Regenerate the session ID.
6. Store only the user ID and minimal session metadata.
7. Load roles and permissions server-side.
8. Redirect or return authenticated response.
9. On logout, invalidate the session and regenerate it.

## Authorization flow

```text
Request
  → SessionManager
  → AuthMiddleware
  → PermissionMiddleware
  → Controller
  → Service
```

Examples:

- Public product listing: no login required.
- Checkout: guest or authenticated user.
- Account dashboard: authenticated user required.
- Admin catalog management: `catalog.manage`.
- Role management: `roles.manage`.
- Order management: `orders.manage`.

# 7. Security Architecture

The future implementation should include:

- `password_hash()` with the default strong PHP algorithm.
- `password_verify()` for authentication.
- PDO prepared statements for every query.
- Server-side validation of all submitted fields.
- Session ID regeneration after login.
- Secure session cookie settings.
- CSRF tokens for state-changing requests.
- Output escaping using `htmlspecialchars()`.
- Upload validation by size, extension, and MIME type.
- Upload storage outside the public web root.
- No payment card storage.
- Server-side recalculation of order totals.
- Server-side inventory validation.
- Login attempt tracking through `login_attempts`.
- Temporary account throttling after repeated failures.
- Audit logging for:
  - Login failures.
  - Role changes.
  - Permission changes.
  - User suspension.
  - Product changes.
  - Inventory adjustments.
  - Order status changes.
- Database credentials stored in local environment configuration, not HTML or JavaScript.
- Generic user-facing errors and detailed local logs.
- Explicit error handling rather than silent fallbacks.

Because the system is localhost-only, a full production deployment stack is unnecessary. However, the application should still follow secure backend boundaries so local development does not establish unsafe patterns.

# 8. Architectural Recommendations

## Maintainability

- Keep the existing frontend presentation.
- Move catalog data out of `store.js` only after the API layer is ready.
- Use repositories for SQL and services for business logic.
- Keep migrations versioned.
- Use consistent JSON responses.
- Replace hardcoded order and customer fallback data with explicit empty states.

## Scalability

- Separate products from product variants.
- Store historical order snapshots.
- Use role-permission relationships rather than hardcoded admin checks.
- Support both guest carts and authenticated carts.
- Use inventory records instead of an `in_stock` boolean.
- Keep order status and payment status separate.

## Performance

- Add indexes on:
  - User email.
  - Product slug.
  - Variant SKU.
  - Order number.
  - Order user and status.
  - Cart user/session.
  - Inquiry status.
  - Promotion code.
- Load only the fields needed for catalog cards.
- Use transactions for checkout.
- Avoid querying product data repeatedly inside loops.

## Compatibility

- Continue serving existing HTML from XAMPP.
- Use relative or configurable application URLs instead of assuming `/`.
- Integrate one module at a time.
- Preserve the existing CSS classes and page layout.
- Keep `localStorage` temporarily as a guest fallback only if necessary, but do not use it as the source of truth for authenticated orders.
